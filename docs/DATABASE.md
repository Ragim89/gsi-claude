# База данных GSI ONE

PostgreSQL 16. Схема развивается только миграциями (`apps/api/migrations/*.sql`), которые применяются раннером `src/db/migrate.ts` — по одной в транзакции, с записью в `schema_migrations`. Вручную схему не меняют.

Актуально после миграции 012.

---

## Принципы

1. **Изоляция — в базе, а не в коде.** Приложение подключается ролью `gsi_app` (`NOSUPERUSER`, `NOBYPASSRLS`). На всех бизнес-таблицах включён Row-Level Security; политики читают контекст транзакции (`app.user_id`, `app.branch_id`, `app.country_id`, `app.scope`, `app.permissions`). Подробнее — [`ROLES_AND_PERMISSIONS.md`](ROLES_AND_PERMISSIONS.md).
2. **Дочерняя запись не может оказаться в чужом офисе.** Составные внешние ключи `(id, branch_id)` плюс триггеры наследования (`trg_inherit_job_branch`, `trg_inherit_client_branch`, `trg_inherit_invoice_branch`, `trg_inherit_asset_branch`).
3. **Бизнес-данные не удаляются.** `deleted_at` + `app_is_live()` в политиках: архив скрыт от всех запросов, а не от тех, где не забыли фильтр.
4. **Деньги — `numeric`**, никогда не float. Каждая сумма хранится в валюте офиса и в валюте консолидации по курсу даты.
5. **Нумерация документов — счётчик в транзакции** (`next_doc_number`), не `MAX(id)+1`.

## Заявка: ключевые поля

| Поле | Смысл |
|---|---|
| `job_number` | `TR-J-2026-00001` — офис, тип документа, год, порядковый номер |
| `branch_id` | офис, отвечающий за работу |
| `requesting_branch_id` | офис, который попросил, если это другой офис |
| `client_id`, `client_contact_id`, `contract_id` | с кем и на основании чего |
| `client_reference` | номер этой заявки у клиента |
| `type` | тип услуги |
| `status`, `status_before_hold` | состояние и куда вернуться после снятия с паузы |
| `priority` | low / normal / high / urgent |
| `assigned_inspector_id` | ведущий (дублирует запись в `job_assignments`) |
| `requested_date` | дата, о которой просил клиент (календарный день) |
| `scheduled_at` | когда мы планируем быть на месте (момент времени) |
| `location`, `city`, `port_id` | где |
| `object_kind`, `vessel_or_object`, `container_no`, `transport_ref` | на чём |
| `commodity_id`, `commodity`, `quantity_value`, `quantity_unit`, `quantity` | что и сколько |
| `instructions` | что просил клиент |
| `internal_notes` | внутреннее, клиенту не печатается |
| `version` | оптимистичная блокировка; растёт триггером |
| `deleted_at` | архив (не то же самое, что статус `cancelled`) |

Почему таблица называется `inspection_jobs`, а не `jobs`: переименование затронуло бы шесть миграций, пять внешних ключей, все политики RLS, выпущенные отчёты и проводки — без единого выигрыша.

## Нумерация документов

```sql
next_doc_number(branch_id, kind) → 'TR-J-2026-00001'
```

Счётчик — строка в `doc_counters (branch_id, kind, year)`, увеличиваемая `INSERT … ON CONFLICT DO UPDATE … RETURNING` внутри транзакции заявки. Два параллельных создания получают два разных номера: проверено тестом, который открывает десять заявок одновременно. Функция `SECURITY DEFINER` и проверяет, что вызывающий имеет отношение к офису.

Типы: `J` — заявка, `R` — отчёт, `I` — счёт.

## Индексы

Частичные индексы «только живые записи» под то, как экраны действительно фильтруют:

```
jobs_active_idx      (branch_id, status)    WHERE deleted_at IS NULL
jobs_priority_idx    (branch_id, priority)  WHERE deleted_at IS NULL
jobs_scheduled_idx   (scheduled_at)         WHERE deleted_at IS NULL
jobs_requested_idx   (requested_date)       WHERE deleted_at IS NULL
jobs_updated_idx     (updated_at DESC)      WHERE deleted_at IS NULL
jobs_contract_ref_idx(contract_id)          WHERE contract_id IS NOT NULL
job_assignments_job_idx / _user_idx         WHERE removed_at IS NULL
job_status_history_job_idx (job_id, created_at)
```

Уникальные частичные индексы там, где уникальность нужна только среди живых записей: инвентарный номер актива, номер контракта, основной контакт клиента, ведущий на заявке.
