# Правила выполнения фаз

Свод правил, по которым велись PHASE 0–7. Он не описывает, *что* строить — это [`IMPLEMENTATION_PLAN.md`](IMPLEMENTATION_PLAN.md), — он описывает, **как** работать, чтобы следующая фаза не сломала предыдущую.

Правила обязательны для каждой фазы. Отступление допустимо только осознанно и с объяснением в финальном отчёте.

---

## 1. Перед тем как писать код

1. **Сначала аудит.** Прочитать существующий модуль, миграции, права и тесты по теме фазы. Отчёт начинается с того, что уже было.
2. **Не создавать второй конкурирующий модуль.** Существующий рабочий модуль развивается, а не заменяется параллельным. Если кажется, что проще написать рядом — это признак, что аудит не закончен.
3. **Сохранять архитектуру.** Модульный монолит NestJS + сырой SQL, React + TanStack Query, изоляция в PostgreSQL через RLS. Новый слой абстракции нужно обосновать, а не ввести походя.

## 2. Данные

4. **Только PostgreSQL и только миграции.** Схема меняется файлом `apps/api/migrations/NNN_*.sql`, применяемым раннером. Руками схему не правят, откатов нет — вперёд и только вперёд.
5. **Миграции аддитивны и обратно совместимы.** Сначала прогон на клоне рабочей базы, потом на ней самой. До и после — счётчики по всем затронутым таблицам; расхождение объясняется или устраняется.
6. **Исторические данные не теряются.** Ни одной строки, ни одного файла, ни одного номера документа.
7. **Историю не выдумывать.** Если прошлые записи нельзя восстановить достоверно, их не создают: поле остаётся `NULL`, запись помечается (`is_legacy`) и об этом пишут в документации.
8. **Неизменяемое — неизменяемо грантами, а не обещаниями.** У `gsi_app` есть `SELECT` и `INSERT` и нет `UPDATE`/`DELETE` на журнале аудита, историях статусов и цепочке хранения. Ошибка исправляется новой записью.
9. **Бизнес-записи архивируются, а не удаляются** (`deleted_at`), и архив скрыт политикой, а не фильтром в запросе.

## 3. Доступ и целостность

10. **RBAC и RLS на сервере.** Право проверяется декоратором на маршруте, видимость строк — политикой в базе. Интерфейс ничего не защищает: он решает, что показывать.
11. **Аудит.** Каждое значимое действие — строка в `audit_logs`: кто, что, когда, над чем, с чем до и после.
12. **Валидация на сервере.** DTO с декораторами, вложенные объекты — с `@ValidateNested`. Принять поле и молча его не использовать нельзя.
13. **Критические операции — в одной транзакции.** Статус, история, аудит и побочные записи пишутся вместе или не пишутся вовсе. Статус меняет только движок переходов, свободного `PATCH status` не существует.
14. **Оптимистичная блокировка** там, где два человека могут править одну форму: устаревшая версия получает 409, а не затирает чужую правку.
15. **Разделение обязанностей.** Кто сделал — не проверяет и не утверждает себя. Исключение — именное право, не входящее ни в одну роль по умолчанию.

## 4. Функциональность

16. **Никакой имитации.** Кнопка либо работает, либо её нет. Запрещены выдуманные числа, заглушки под видом аналитики и экраны, за которыми ничего не стоит.
17. **Сквозная работоспособность:** от элемента интерфейса до строки в PostgreSQL и обратно.
18. **Секреты не попадают в репозиторий.** Ключи и пароли — через переменные окружения; значения по умолчанию годятся только для разработки.
19. **Три языка (EN/RU/TR)** во всём интерфейсе, без строк в коде. Язык документа отделён от языка интерфейса.
20. **Мобильные ширины проверяются:** 390×844, 768×1024 и десктоп. Горизонтальной прокрутки страницы быть не должно.
21. **Предыдущие фазы сохраняются.** Существующие маршруты, форматы номеров, права и экраны продолжают работать.

## 5. Проверка перед завершением фазы

Всё выполняется в Docker. Перечислять проверки вручную больше не нужно — есть две команды:

```bash
bash scripts/verify.sh        # модульные → интеграционные → lint → typecheck → сборка API → сборка web
bash scripts/verify-full.sh   # то же плюс образы Docker, поднятый стенд, /api/health/ready и smoke по всем модулям
```

Обе — докеровское написание npm-скриптов (`npm run verify` в корне и в `@gsi/api`), которые и задают последовательность. `lint` — про API: у web нет конфигурации ESLint, а его `build` запускает `tsc --noEmit`, то есть типы проверяются при сборке.

Сверх этих команд каждая фаза добавляет то, что автоматизировать нельзя:

- **E2E своей фазы** на работающем стенде — реальные данные, реальные файлы, реальные переходы;
- **визуальная проверка** того, что печатается или показывается: PDF открыть и посмотреть, а не поверить коду 200;
- **мобильные ширины** 390×844, 768×1024 и десктоп;
- **документация**: `DATABASE.md`, `API.md`, `WORKFLOWS.md`, `ROLES_AND_PERMISSIONS.md`, `SECURITY.md`, `IMPLEMENTATION_PLAN.md`, `CHANGELOG.md`.

Ни одна упавшая команда не остаётся без исправления или объяснения. Числа в отчёте берутся из вывода раннера и сходятся арифметически.

## 6. Git

22. **Коммит и push — только после зелёной проверки.** Коммиты логические, история не переписывается.
23. **Тег фазы — только на последнем проверенном коммите.**
24. **Опубликованный тег не переносится.** Если после тега потребовалась доработка, создаётся новый тег (`…-verified`), а прежний остаётся на месте.
25. **Следующая фаза не начинается автоматически.**

## Формат финального отчёта

Одним сообщением, в этом порядке; разделы, которых фаза не касалась, опускаются.

**Completed** — что сделано, коротко.
**Audit** — что существовало до фазы и что с этим стало.
**Database Changes** — миграции и их смысл.
**Migration Result** — счётчики до и после, доказательство сохранности.
**Backward Compatibility** — что из прежнего проверено работающим.
**Workflow / Permissions** — состояния, переходы, права, разделение обязанностей.
**Key Guarantees** — главные обещания фазы и чем каждое подтверждено.
**Working E2E** — точное число шагов и проверок, пройденных на стенде.
**Database Counts** — итоговые счётчики по основным таблицам.
**Tests** — таблица: previous / new / unit / integration / total. Числа обязаны сходиться.
**Regression Verification** — точное число проверок и охваченные модули.
**Responsive / Visual Verification** — ширины и экраны, результат осмотра.
**Build / Lint / Typecheck** — перечень команд и их итог.
**Remaining Issues** — честно: что не доделано, что сознательно отложено и почему.
**Manual Actions Required** — что должен сделать человек, или «none».
**Commits / Push / Tag** — хеши, ветка, тег.
**Next Phase** — какая следующая и что она не начата.
