# CURRENT_STATE — аудит репозитория GSI ONE

Дата аудита: 2026-09-23. Ветка `feat/mvp-1`, последний коммит на момент аудита — `5febaa2` («Bulk data import from Excel and CSV»).

Документ описывает **фактическое** состояние кода, а не намерения. Всё, что помечено «работает», проверено на запущенном стенде (`docker compose up`), а не выведено из чтения кода.

## 1. Существующая архитектура

Модульный монолит + SPA, монорепозиторий на npm workspaces.

```
gsi-erp/
├── apps/
│   ├── api/          NestJS 10 (модульный монолит), сырой SQL через pg, без ORM
│   │   ├── migrations/   6 SQL-миграций, применяются своим раннером (src/db/migrate.ts)
│   │   └── src/          auth, admin, crm, operations, documents, finance,
│   │                     reference, assets, export, import, storage, db, common
│   └── web/          React 18 + Vite + TanStack Query + react-router 6 + i18next
├── packages/
│   ├── shared-types/ домены, enum-ы, машина статусов Job, шаблоны чек-листов
│   └── ui-kit/       дизайн-токены (единственный источник фирменных цветов) + React-компоненты
├── docs/             исходная спецификация 00–07 (RU)
└── docker-compose.yml  db (postgres:16) + minio + api + web(nginx)
```

Объём: **≈15 300 строк** TS/TSX/SQL (без node_modules и dist).

Ключевое архитектурное решение, унаследованное из MVP-1 и **сохраняемое**: изоляция данных реализована в PostgreSQL через **Row-Level Security**, а не в коде приложения. API подключается ролью `gsi_app` (`NOSUPERUSER`, `NOBYPASSRLS`), `DbService.tx(user, fn)` открывает транзакцию и кладёт контекст пользователя в `set_config('app.user_id'|'app.branch_id'|'app.role', …, true)` (transaction-scoped, поэтому пул соединений не протекает между запросами). Политики опираются на функции `app_user_id()`, `app_branch_id()`, `app_role()`, `app_is_hq()`, `app_sees_finance()`.

Это сильная сторона проекта: даже ошибка в сервисе или подделанный `branchId` в запросе не дают доступа к чужому филиалу — проверено (супервайзер RO видит 0 заявок TR; подстановка чужого `branchId` возвращает пустой результат).

## 2. Технологический стек

| Слой | Технология | Оценка |
|---|---|---|
| Backend | NestJS 10, TypeScript 5.5, Node 20 | подходит для production, оставляем |
| Доступ к БД | `pg` + сырой SQL, ручные миграции | оставляем; SQL нужен для RLS и агрегатов, ORM тут только мешал бы |
| БД | PostgreSQL 16, RLS, SECURITY DEFINER функции | оставляем, это ядро безопасности |
| Файлы | S3-совместимое хранилище (MinIO в dev) через `@aws-sdk/client-s3` | оставляем, абстракция `StorageService` уже есть |
| PDF | puppeteer-core + Chromium в образе API | оставляем |
| Frontend | React 18, Vite 5, TanStack Query 5, react-router 6 | оставляем |
| i18n | i18next + react-i18next, 3 языка (en/ru/tr) | оставляем, расширяем |
| Стили | CSS + дизайн-токены из `packages/ui-kit/src/tokens.ts` | оставляем; цвета нигде не захардкожены |
| Инфраструктура | Docker Compose (4 сервиса) | оставляем |

**Важное ограничение среды разработки:** на машине разработчика **нет Node и npm** (`node -v` → command not found). Всё — сборка, typecheck, тесты — выполняется только внутри Docker. Это должно быть зафиксировано в документации и в скриптах, иначе «запусти тесты» будет невыполнимой инструкцией.

## 4. Существующая схема БД

18 таблиц:

```
branches, users, clients, inspection_jobs, job_checklist_items, media_attachments,
reports, doc_counters, fx_rates, invoices, invoice_lines, expenses, ledger_entries,
finance_daily_agg, commodities, ports, assets, asset_depreciation
```

Сильные стороны:
- UUID-ключи, `created_at` / `updated_at` с триггерами, `created_by`.
- Составные внешние ключи `(id, branch_id)` + триггеры наследования филиала (`trg_inherit_job_branch`, `trg_inherit_invoice_branch`, `trg_inherit_asset_branch`) — дочерняя запись физически не может оказаться в другом филиале.
- RLS включён на всех бизнес-таблицах.
- Деньги — `numeric`, не float.
- 25 индексов.

Чего нет:
- Иерархии `organizations → countries → offices → departments` — только плоская таблица `branches`.
- Таблиц прав: `roles`, `permissions`, `role_permissions`, `user_roles`.
- `audit_logs`, `notifications`, `activity_logs`.
- `contracts`, `client_contacts`.
- `job_status_history`, `job_assignments` (назначение хранится одним полем в заявке).
- `inspections` как отдельной сущности — чек-лист висит прямо на заявке.
- Всего блока LIMS: `lab_samples`, `lab_results`, `laboratories`, `test_methods`, `test_requests`.
- `report_versions`, `certificates`.
- `quotes`, `services`, `prices`, `payments` (оплата — проводка, отдельной сущности нет), `job_costs`.
- `documents` как общего реестра (файлы привязаны только к пунктам чек-листа).
- Мягкого удаления: `DELETE FROM` физически удаляет строки в 6 местах (заявки, контрагенты, счета, расходы, активы, медиа).

## 5. Существующее API

Префикс `/api`, 12 контроллеров, ~70 маршрутов:

```
/api/health
/api/auth        login, refresh, me
/api/users       список, создание, изменение
/api/branches    список, карточка, сравнение, реквизиты, фото
/api/clients     CRUD
/api/jobs        CRUD + assign/start/submit/return/approve/cancel + чек-лист + загрузка фото
/api/media       удаление вложения
/api/reports     список, PDF
/api/public      verify/:token (без авторизации)
/api/finance     dashboard, SSE stream, invoices, expenses, fx-rates
/api/assets      CRUD, summary, dispose, photo, depreciation/run
/api/reference   commodities, ports
```

Что есть: валидация через `class-validator` + глобальный `ValidationPipe` (`whitelist`, `forbidNonWhitelisted`), фильтр ошибок PostgreSQL (`PgExceptionFilter`), фильтрация и поиск в списках.

Чего нет: **пагинации** (везде жёсткий `LIMIT 500`), сортировки по параметру, единого формата ошибок, версионирования API, ограничения частоты запросов.

**Отсутствуют полностью.** Ни одного теста, нет ни jest, ни vitest, ни supertest, нет eslint и prettier, нет CI. Единственный способ проверки сегодня — ручные сценарии через curl и браузер.

## 8. Найденные проблемы

### 8.1 Критические (блокируют дальнейшую разработку)

| # | Проблема | Последствие |
|---|---|---|
| C1 | Нет тестов и линтера | любая правка RLS или схемы может незаметно сломать изоляцию филиалов |
| C2 | Нет audit log | требование спецификации; чем позже добавить, тем больше мест придётся переписывать |
| C3 | Права — строка роли, разбросанная по коду (`@Roles('admin')`, списки ролей в SQL-функциях, дубль тех же списков во фронтенде) | добавление роли (например, Lab Manager) требует правок в десятке мест |
| C4 | Нет иерархии организация → страна → офис | вся модель доступа завязана на плоский `branch_id`; переделка позже затронет все RLS-политики |
| C5 | Физическое удаление бизнес-данных | безвозвратная потеря счетов, заявок, отчётов |

### 8.2 Важные

| # | Проблема |
|---|---|
| I1 | Нет пагинации: `LIMIT 500` в списках, фронт грузит всё одним запросом |
| I2 | Нет ограничения частоты запросов на `/auth/login` — перебор паролей ничем не сдерживается |
| I3 | Нет `helmet` и заголовков безопасности |
| I4 | Refresh-токены без серверного отзыва: увольнение сотрудника действует только через 7 дней |
| I5 | Токены в `localStorage` (помечено `// ASSUMPTION` в коде) — уязвимо к XSS |
| I6 | Нет структурированного логирования и метрик; `/api/health` проверяет только `SELECT 1` |
| I7 | Демо-данные засеваются на старте контейнера (`SEED_ON_START`) — в production так делать нельзя |
| I8 | Формат номера (`TR-J-2026-00001`) не совпадает с целевым из ТЗ (`GSI-TR-2026-000001`) |
| I9 | Нет обработки N+1 и явных лимитов на размер ответа |
| I10 | Нет `THIRD_PARTY_LICENSES.md` и фиксации лицензий зависимостей |

### 8.3 Технический долг

- Роль `client` (личный кабинет клиента) объявлена в enum, но нигде не используется — «мёртвая» роль.
- `lab_technician` объявлен, но LIMS нет — роль ничего не даёт.
- Чек-лист и «инспекция» смешаны: нет времени начала/окончания, подписи, отдельного статуса инспекции.
- Отчёт один на заявку, без версий: повторное утверждение перезапишет документ.
- Оплата счёта — только проводка, отдельной сущности `payments` нет, что затруднит сверку.
- Расход считается оплаченным в момент создания (нет кредиторской задолженности).
- `tmp-demo/` в корне репозитория (в `.gitignore`, но лежит в рабочей копии).
- Дублирование списков ролей: `FINANCE_ROLES` в shared-types, `app_sees_finance()` в SQL, `finance` в `Layout.tsx`, `FINANCE` в `App.tsx` — четыре источника одной истины.

### 8.4 Безопасность — что уже сделано правильно

Не всё плохо, и это важно не сломать:
- Секретов в репозитории нет, `.env` в `.gitignore`, есть `.env.example`.
- В production `JWT_*_SECRET` обязателен (dev-fallback только при `NODE_ENV !== production`).
- Параметризованные запросы везде — SQL-инъекции закрыты.
- Загрузка файлов: белый список MIME, лимит размера, пересжатие через sharp.
- Приложение ходит в БД под ролью без права обходить RLS.
- Пароли — bcrypt, не хранятся и не логируются.

## 10. Рекомендуемая целевая архитектура

Менять стек не нужно. Нужно достроить фундамент и домены.

1. **Иерархия владения.** `organizations → countries → offices → departments → users`. `branches` становится `offices` (или сохраняется как алиас) без потери данных: код филиала и все связи переносятся миграцией. Контекст доступа расширяется с `app.branch_id` до `app.office_id` + `app.country_id` + `app.scope` (global / country / office / own).
2. **RBAC.** Таблицы `permissions`, `roles`, `role_permissions`, `user_roles`. Проверка — один guard по коду права (`job.approve`), а не по имени роли. RLS продолжает отвечать за строки, RBAC — за действия. Списки ролей в SQL заменяются на проверку права.
3. **Audit log.** Одна таблица `audit_logs` + сервис, вызываемый из всех переходов состояний, плюс триггеры БД на критичные таблицы. Пользователю недоступен на запись (нет GRANT на UPDATE/DELETE).
4. **Workflow engine.** Единый модуль переходов: `validate → authorize → execute → audit`. Машина статусов Job уже есть в `shared-types` — расширить её на Inspection, Sample, Lab Test, Report.
5. **Мягкое удаление.** `deleted_at` на бизнес-таблицах, RLS-политики исключают удалённые, эндпоинты `DELETE` переводятся в архивирование.
6. **Пагинация** во всех списках (`limit`/`offset` + `total`), единый конверт ответа.
7. **Тесты** внутри Docker: vitest (unit) + supertest (интеграционные, на реальной БД) + сквозной тест приёмочного сценария.
8. **PWA**: manifest, service worker, нижняя навигация для инспектора, фундамент для offline (очередь операций).

Порядок работ — в `IMPLEMENTATION_PLAN.md`.
