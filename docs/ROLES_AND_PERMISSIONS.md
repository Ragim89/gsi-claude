# Роли, права и изоляция данных

Документ описывает, как в GSI ONE устроен доступ: кто что может делать (права) и какие строки видит (область видимости). Актуально с PHASE 4.

---

## Три уровня защиты

Доступ проверяется трижды, и каждый уровень самостоятелен:

| Уровень | Что решает | Где реализовано |
|---|---|---|
| Интерфейс | что показывать: пункты меню, кнопки | `useAuth().can('job.approve')` |
| API | можно ли выполнить действие | `@RequirePermission('job.approve')` |
| База данных | какие строки существуют для этого пользователя | Row-Level Security |

Интерфейс ничего не защищает — он только не предлагает того, что всё равно закончится отказом. Настоящая проверка действия — в API, настоящая проверка данных — в PostgreSQL.

---

## Право (permission)

Право — это глагол в форме `объект.действие`: `job.approve`, `invoice.pay`, `audit.read`. Каталог хранится в таблице `permissions` и продублирован типом `Permission` в `packages/shared-types/src/rbac.ts`, чтобы опечатка была ошибкой компиляции, а не молчаливым отказом.

Категории: `operations`, `crm`, `documents`, `finance`, `assets`, `reference`, `admin`, `data`.

Права операционного блока после PHASE 3:

| Право | Что разрешает |
|---|---|
| `job.read` / `job.read_history` | видеть заявки / их историю статусов |
| `job.create` / `job.update` | создавать / редактировать |
| `job.assign` | назначать и снимать исполнителей |
| `job.change_status` | вести заявку по жизненному циклу (подтверждение, этапы, пауза) |
| `job.start` / `job.submit` | начать полевые работы / сдать на проверку |
| `job.approve` | утвердить и выпустить отчёт |
| `job.cancel` | отменить или вернуть на доработку |
| `job.close` | закрыть завершённую заявку |
| `job.archive` / `job.restore` | убрать в архив / вернуть из архива |
| `job.read_finance` | видеть счета и затраты на карточке заявки |

`job.delete` из PHASE 1 переименовано в `job.archive`: удаления заявок в системе нет и не было — было архивирование, которое называлось неправильно.

Права инспекций, добавленные в PHASE 3 → PHASE 4:

| Право | Что разрешает |
|---|---|
| `inspection.read` | видеть инспекции, их чек-лист, замечания, замеры, фото и историю |
| `inspection.create` / `inspection.update` | открыть инспекцию по заявке / править её данные |
| `inspection.assign` | назначать и снимать исполнителей на инспекции |
| `inspection.start` | начать полевые работы |
| `inspection.complete` | завершить инспекцию и сдать её на проверку |
| `inspection.review` | вернуть инспекцию на доработку |
| `inspection.approve` | утвердить инспекцию, а также открыть утверждённую заново |
| `inspection.cancel` | отменить, приостановить и возобновить |
| `inspection.add_finding` / `inspection.add_measurement` | записывать замечания / замеры |
| `inspection.archive` / `inspection.restore` | убрать в архив / вернуть из архива |

Права выданы не вручную, а выведены из уже существующих: кто видел заявки — видит инспекции, кто создавал заявки — создаёт инспекции, кто начинал работы — начинает и завершает их, кто утверждал заявки — проверяет и утверждает инспекции. Отдельно пробоотборщик (`sampler`) получил право видеть инспекции, начинать их и записывать замечания и замеры: это тоже полевая работа.

Сдать работу и судить о работе — разные права: `inspection.complete` позволяет и завершить инспекцию, и передать её на проверку, а `inspection.review` нужно лишь для того, чтобы вернуть её автору.

## Роль (role)

Роль — именованный набор прав плюс **область видимости**:

| Область | Что видно |
|---|---|
| `global` | вся группа |
| `country` | все офисы одной страны |
| `office` | свой офис |
| `own` | только свои записи: заявки и инспекции, на которые этот сотрудник назначен |

Предустановленные роли (`roles`, 15 штук):

| Код | Название | Область |
|---|---|---|
| `admin` | Системный администратор | global |
| `cfo` | Финансовый директор группы | global |
| `country_manager` | Руководитель по стране | country |
| `office_manager` | Руководитель офиса | office |
| `supervisor` | Супервайзер | office |
| `operations` | Операционный отдел | office |
| `finance_controller` | Финансовый контролёр | office |
| `sales` | Продажи | office |
| `report_reviewer` | Проверяющий отчёты | office |
| `lab_manager` | Руководитель лаборатории | office |
| `lab_analyst` | Лаборант | office |
| `inspector` | Инспектор | own |
| `sampler` | Пробоотборщик | own |
| `viewer` | Наблюдатель | office |
| `client` | Клиент (личный кабинет) | own |

Роли — это **данные**, а не код. Чтобы дать руководителю лаборатории право утверждать результаты, достаточно поставить галочку на экране «Роли»; релиз не нужен.

Пользователь может иметь несколько ролей: права складываются, область видимости берётся самая широкая.

## Как это работает в рантайме

1. При входе `auth_find_user()` (SECURITY DEFINER, работает до появления контекста) возвращает пользователя, его роли, область и права.
2. В токен кладутся **коды ролей**, а не права: токен остаётся коротким, а изменение состава прав роли действует для всех в течение минуты, без повторного входа.
3. На каждом запросе guard:
   - читает роли пользователя из БД (кэш 10 секунд) — поэтому **отзыв роли действует почти сразу**, а не через 15 минут жизни токена;
   - разворачивает роли в права по кэшу (обновляется раз в минуту и принудительно при изменении роли);
   - проверяет `@RequirePermission(...)`.
4. `DbService.tx()` кладёт в транзакцию контекст: `app.user_id`, `app.branch_id`, `app.country_id`, `app.scope`, `app.permissions`.
5. Политики RLS читают этот контекст через функции `app_scope()`, `app_country_id()`, `app_has_perm(code)`, `app_can_see_branch(branch_id)`, `app_is_live(deleted_at)`.

Приложение подключается к базе ролью `gsi_app` — не владелец таблиц, `NOBYPASSRLS`. Даже ошибка в сервисе или подделанный `branchId` в запросе не дают чужих данных.

## Иерархия

```
organizations
└── countries            (страна; ISO-код, язык, часовой пояс)
    └── branches         (офис = юрлицо: своя валюта, бланк, реквизиты)
        └── departments  (отдел: операции, лаборатория, финансы, ...)
            └── users
```

Офис — это существующая таблица `branches`: переименования не было, чтобы не ломать работающие данные и код. Страна проставляется триггером по ISO-коду офиса; открытие офиса в новой стране создаёт страну автоматически.

## Архивирование вместо удаления

Бизнес-записи (контрагенты, заявки, счета, расходы, активы) не удаляются физически: у них проставляется `deleted_at`. Скрытие архива реализовано **в самих политиках** (`app_is_live(deleted_at)` в USING), а не в отдельных запросах — иначе первый же забытый фильтр показал бы удалённое.

Следствие, о котором стоит знать: пометить запись архивной можно только в транзакции, которой разрешено видеть архив (`DbService.tx(user, fn, { includeArchived: true })`), потому что обновлённая строка обязана остаться видимой для той же политики. Этот же режим понадобится экрану восстановления.

Отчёты в этот список не входят: выпущенный отчёт не удаляется вообще, он может быть только отозван — и отзыв виден.

## Журнал аудита

Таблица `audit_logs` — только на добавление: у роли `gsi_app` нет прав `UPDATE` и `DELETE` на неё. Ни администратор через интерфейс, ни ошибка в коде не могут переписать историю.

Записывается: вход (в том числе неудачный, с причиной), создание и изменение записей, все переходы статусов, утверждение и выпуск отчётов, изменение ролей и прав, архивирование. Для изменений хранится только то, что действительно изменилось — «было» и «стало».

Чтение журнала требует права `audit.read` и ограничено областью видимости читающего.

## Как добавить право или роль

1. Право: добавить строку в `permissions` (миграция) и в `PERMISSIONS` в `packages/shared-types/src/rbac.ts`, затем повесить `@RequirePermission('новое.право')` на нужные маршруты.
2. Роль: добавить строку в `roles` (или создать её на экране «Роли», когда появится создание) и назначить права.
3. Изоляция строк: если появилась новая таблица с `branch_id`, включить RLS и создать политику по образцу: `USING (app_can_see_branch(branch_id) AND app_is_live(deleted_at))`.

Проверка: `docker compose --profile test run --rm test` — набор `test/isolation.spec.ts` и `test/rbac.spec.ts` существует именно для того, чтобы такие изменения не ломали изоляцию незаметно.
